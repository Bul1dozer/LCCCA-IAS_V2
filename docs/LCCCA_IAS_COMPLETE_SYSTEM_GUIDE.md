# 1. Introduction to LCCCA-IAS

LCCCA-IAS is the Life Changing Christian Church Academy Invoice Automation System. It is a school finance and administration system for managing learners, parents or guardians, fee assignments, invoices, payments, balances, reports, and accountability records.

The system is different from ordinary record keeping because it does not only store names and amounts. It connects each financial action to a learner, parent, invoice, payment, ledger entry, and audit record. This makes it easier to see who was billed, what was charged, who paid, what remains outstanding, and which staff action created or changed a record.

The normal workflow is:

Parent and learner records -> fee allocation -> invoice generation -> payment recording -> balance updates -> ledger and audit records -> reporting.

The expected users are school administrators, finance staff, reception staff, and system operators. In the current implementation, almost every operational screen and API requires administrator permission.

# 2. User Roles and Permissions

The user table stores a `role` value for each user. The implemented authorization system recognizes `Administrator` and `admin` as administrator roles. It also has a `Role` table with a `permissions` text field, and a user can be treated as an administrator if the matching role grants `admin`, `administrator`, or `*`.

Authentication means proving who you are, usually by logging in with a username and password, and sometimes a two-factor code. Authorization means deciding what that authenticated user is allowed to do.

Implemented role behavior:

| Role | Current access |
| --- | --- |
| Administrator/admin | Can access protected API operations for learners, parents, fees, invoices, payments, imports, reports, audit logs, reconciliation, month-end, email logs, and settings. |
| Custom role with admin permission | Can be treated as admin if a matching `Role` row grants admin-like permissions. |
| Non-admin user | Authenticates, but protected operations return "Administrator privileges required." |
| Disabled user | Cannot authenticate or use protected APIs. |

The protected route groups are: Dashboard, Learners, Parents, Fee Catalogue, Fee Structures, Invoices, Payments, Email Logs, Bank Reconciliation, Reports, Audit Log, Month-End, Data Import, and Settings. The login, 2FA challenge, forgot-password, and reset-password endpoints are public by design.

Important limitation: the HTML page routes themselves render templates without checking login first. The data on those pages comes from protected API calls, so unauthenticated users cannot load live records, but the page shell may still appear.

# 3. Login and Security

The user opens `/login`, enters a username and password, and submits the form. If the username and password are valid and the account is active, the system creates a server-side session and sends the user to the Dashboard.

If login fails, the system returns "Invalid username or password." Failed attempts are rate limited. By default, five failed attempts in the configured time window trigger "Too many attempts. Try again later."

If the account is disabled, login fails because authentication only accepts active users. If the user has two-factor authentication enabled, the password step does not fully log them in. Instead, the system opens a second step asking for an authenticator code.

Session controls:

| Control | Current behavior |
| --- | --- |
| Session cookie | `lcca_session` |
| Default session lifetime | 8 hours unless changed by environment configuration |
| Secure cookie | Enabled automatically in production unless overridden |
| SameSite | Defaults to `lax` |
| Logout | Clears the session and writes an audit entry when a user was logged in |
| CSRF | API-changing requests use an `lcca_csrf` cookie and `X-CSRF-Token` header in the frontend |
| CORS | Production requires trusted origins to be configured |

Production requirements include a session secret, trusted CORS origins, and a TOTP encryption key. The application refuses to start in production if some required security settings are missing.

Important security warning: seed data creates an administrator account with demo credentials when the database is empty. The login page also displays demo credentials. These must not remain valid in a real production deployment.

# 4. Two-Factor Authentication

Two-factor authentication, or 2FA, adds a second proof after the password. LCCCA-IAS uses TOTP codes, the six-digit codes generated by authenticator apps.

Setup works like this:

1. An authenticated administrator opens Settings.
2. The user chooses the 2FA tab.
3. The system creates a TOTP secret and stores it encrypted.
4. The system returns a QR code and setup URI.
5. The user scans the QR code with an authenticator app.
6. Setup is not complete until the user enters a valid current code.
7. After a valid code, `totp_enabled` is set to true and an audit record is written.

Login after 2FA is enabled:

1. The user enters username and password.
2. The system creates a pending 2FA session, not a full login session.
3. The user enters the authenticator code.
4. If the code is valid, the normal session is created.
5. If the code is invalid, the system records a failed 2FA login and limits repeated attempts.

Disabling 2FA requires the current password and, if 2FA is enabled, a valid current TOTP code. The stored TOTP secret is then deleted.

Backup codes were not found in the implementation.

# 5. Forgot Password and Password Reset

The login page includes a recovery area. A user enters a username and email address. The system always returns a generic message so that attackers cannot easily discover whether an account exists.

If the details match an active user, the system marks older unused reset tokens as used, creates a new token, stores only a digest of the token, sets a one-hour expiry, and attempts delivery through the password reset email helper.

In normal mode, the raw reset token is not returned to the browser. In development only, if `LCCA_ALLOW_DEV_RESET_TOKEN=1` and the app is not in production, the response can include the token and reset link for testing.

The reset token is single-use. Invalid, already-used, and expired tokens are rejected. A successful reset updates the password and marks the token as used. The code does not explicitly revoke other existing sessions after password reset.

Email delivery depends on environment and email configuration. When delivery is not configured, the system uses fallback/test behavior rather than guaranteed real mail.

# 6. Changing a Password

The password change option is in Settings. The user enters the current password, a new password, and confirmation.

The system checks:

| Check | Result if it fails |
| --- | --- |
| Current password is correct | "Current password is incorrect." |
| New password and confirmation match | "New passwords do not match." |
| New password is at least 8 characters | "Password must be at least 8 characters." |
| New password differs from current password | "New password must be different from the current password." |

After a successful change, the system writes an audit log entry, commits the new password hash, and refreshes the session for the same user. The password policy is currently minimum-length based; it does not enforce uppercase, lowercase, number, or symbol rules.

# 8. Learner Management

Learners are managed on the Learners screen. Staff can add a learner with full name, grade, class, date of admission, status, and physical address. The backend schema also supports ID number and date of birth, but the current learner form does not expose those fields.

When a learner is created, the system generates a learner code, sets the balance to zero, auto-assigns matching mandatory fees, writes an audit log, and commits the record.

The learner table shows Learner ID, Full Name, Grade, Class, Admission Date, Status, Balance, and Actions. The profile view shows parent/guardian links, physical address, admission information, status, balance, and a link to the learner statement report.

The permanent learner code is intended to be unique. The route generator creates a 10-digit code using `YYYYMMDD` plus a two-digit sequence, for example `2026071401`. The model also has a fallback generator that can create a 10-digit numeric code if the provided code is invalid. Existing learner codes are protected by a database uniqueness constraint.

Users do not edit learner codes in the current screen.

Deleting a learner is implemented as deactivation, not hard deletion. The backend refuses to deactivate a learner with a non-zero ledger balance. This protects financial records. The modal wording says related records will be removed and cannot be undone, but the backend actually performs a soft delete when allowed.

| Grade | Grade 3 |
| Class | 3A |

# 9. Grade Grouping and Filtering

Supported grades are Baby Class, Toddler Class, Grade 0, Grade 1, Grade 2, Grade 3, Grade 4, Grade 5, Grade 6, Grade 7, Grade 8, Grade 9, and Grade 10.

The API supports listing learners by grade and filtering the learners list by an exact grade parameter. It also supports grouped results through `/api/learners/by-grade`.

The current Learners screen has a text search and status filter. It does not show a dedicated grade dropdown. Staff can search for "Grade 7" to narrow the visible list, and integrations can call the grade filter directly.

When a learner changes grade, the update route auto-assigns any newly applicable mandatory fees. Historical invoices are not changed by a grade update. They remain as records of what was billed at the time.

# 11. Learner-Parent Relationships

Learners and parents are connected through relationship records. A relationship stores learner, parent, relationship type, and an `is_primary` flag.

The current parent link screen lets staff choose a learner and relationship type: Mother, Father, Guardian, or Other. It does not expose primary-parent selection. The seed data creates primary links, and invoice display can use a primary parent for legacy learner invoices when available.

For parent aggregated invoices, the billing party is the parent selected in the invoice form. The system gathers that selected parent's active linked learners.

Incorrect links can cause the wrong children to appear on a parent invoice, or prevent a child from being included. Staff should verify the parent profile and linked learners before generating a parent invoice.

# 12. Fee Catalogue and Grade-Based Fees

The Fee Catalogue is the current fee system. A fee item has name, category, description, frequency, amount, mandatory status, active status, applicable grades, applicable classes, sort order, and optional effective dates.

The screen has three tabs: Catalogue, Learner Profiles, and Transport Routes.

Grade-based fees are normal fee catalogue items with applicable grades. Mandatory fee items are auto-assigned to learners when they are created, imported, or when the auto-assign action is used. Learner-specific fees are stored as learner fee assignments. A learner assignment can use the catalogue price or a custom amount.

Monthly fees are used for normal monthly invoice generation. Annual and once-off fees are stored and visible in the catalogue but are not included in the monthly invoice generator unless assigned and the generation logic filters for that frequency. Parent aggregated invoices currently collect monthly lines.

Ordinary fee item amounts must be greater than zero through schema and route validation. The database allows fee item amount zero, but the API rejects zero and negative fee items. Invoice item amounts are non-negative, and ledger entries must be positive.

Transport routes are implemented with route name, description, monthly fee, and active status. The current route management screen creates and edits routes. Learners have a `transport_route_id`, but the learner form does not expose assigning a route directly.

Discounts, waivers, credits, adjustment screens, and reversal workflows are limited. A ledger adjustment helper exists in code, but no user-facing adjustment screen was found.

# 13. Invoice Generation

The system supports two invoice types.

Individual learner invoice:

1. Staff choose Invoice For: Learner.
2. Staff select a learner.
3. Staff enter billing period and due date.
4. Staff may select a legacy fee structure, or use the learner's assigned fee profile.
5. The backend creates one learner invoice, creates invoice items, posts a debit ledger entry, writes an audit record, and commits.

Parent aggregated invoice:

1. Staff choose Invoice For: Parent (aggregate linked learners).
2. Staff select a parent.
3. Staff enter billing period and due date.
4. The backend loads active linked learners for that parent.
5. The backend skips any learner already invoiced for that billing period.
6. It collects active monthly fee lines for eligible learners.
7. It creates one invoice with `parent_id` set and `learner_id` empty.
8. Each invoice item stores the learner it belongs to.
9. It posts separate learner ledger debit entries.
10. It returns one combined invoice number and total.

Example: one parent has three linked learners with monthly charges N$ 123.45, N$ 99.99, and N$ 0.01. The tested behavior creates one invoice, three learner-specific invoice items, one combined total of N$ 223.45, and three learner ledger debit entries totalling N$ 223.45.

If one learner has already been invoiced for the billing period, the parent invoice skips that learner and still invoices eligible siblings. If all learners have already been invoiced, or none have billable monthly fees, the request returns an error and no new invoice is created. If the parent has no active linked learners, the request returns "No active learners linked to this parent."

Duplicate parent invoice requests are guarded by learner-level duplicate checks for the billing period. Financial regression tests confirm the second request does not create duplicate invoice, item, or ledger rows.

If an error occurs before commit during parent invoice generation, tests confirm invoice, invoice-item, ledger, and audit rows roll back.

# 14. Invoice Tab and Invoice Display

The Invoices screen is parent-centric in the main table. It displays:

Invoice Number, Parent, Linked Learners, Billing Period, Issue Date, Due Date, Current Charges, Previous Balance, Payments, Outstanding Balance, Status, and Actions.

Parent aggregated invoices show the selected parent as the billing party. Linked learner names appear separately. Legacy learner invoices remain readable by showing the related parent when one can be found, while still preserving the learner name in linked learner display.

Expanding an invoice displays learner-specific line items with learner, line item, and amount.

Search supports parent name and invoice number. Status filtering supports Generated and Sent.

Actions include expand line items, preview PDF, download PDF, send email, and delete. Delete maps to backend voiding behavior, not hard deletion.

# 15. Understanding Financial Calculations

Current charges are the new charges on an invoice. Previous balance is the learner balance before the invoice. Payments made represent payment credits considered by the invoice logic. Outstanding balance is what remains due.

A debit increases what a learner owes. A credit reduces what a learner owes. Ledger entries are the authoritative financial movements. Invoice items explain what makes up the invoice total.

Core rules:

| Rule | Current support |
| --- | --- |
| Invoice total equals sum of invoice items | Tested for parent invoices |
| Invoice charges equal ledger debit totals | Tested for parent invoices |
| Payments reduce correct learner balance | Implemented through ledger credit posting |
| Duplicate parent invoices do not duplicate ledger entries | Tested |
| Decimal calculations are exact to cents | Implemented with Decimal quantization and tested |

Simple example: if a learner owes N$ 200.00, and the school records a N$ 50.00 payment, the ledger has a N$ 200.00 debit and N$ 50.00 credit. The balance is N$ 150.00.

# 16. Payments

Payments are captured on the Payments screen. Staff select a learner, enter amount, date paid, method, optional reference number, and notes.

Implemented payment methods shown on screen are Cash, Bank Transfer, EFT, Card, and Mobile Money.

Payment creation:

1. Validates the learner exists and is active.
2. Validates amount is greater than zero.
3. Rejects duplicate active reference numbers.
4. Optionally rejects overpayments if `OVERPAYMENT_POLICY=reject`.
5. Creates the payment record.
6. Posts a credit ledger entry.
7. Updates the learner balance cache.
8. Writes an audit log.

Partial payments and full payments are naturally supported because payments are credits against a learner's ledger balance. Overpayments are allowed by default as credits unless the overpayment policy is set to reject.

Payment receipts are implemented as PDF responses from `/api/payments/{payment_id}/receipt`.

Payment reversal is implemented. The reverse/delete route marks the payment inactive, voids the related ledger entry, updates balance, and writes an audit entry.

Important limitation: the Payments screen includes an edit button and calls `PUT /api/payments/{id}`, but no matching backend update route was found. Payment editing should be treated as incomplete.

# 17. Voids, Reversals, and Corrections

Financial records should not simply be deleted because the school needs an audit trail. The implemented correction patterns are:

| Area | Implemented behavior |
| --- | --- |
| Invoice delete | Soft-voids the invoice and ledger charges |
| Invoice void | Marks invoice Void and voids related learner ledger debit entries |
| Payment delete | Soft-reverses the payment and voids the payment credit |
| Payment reverse | Marks payment inactive and voids the payment ledger entry |
| Manual adjustments | Helper exists in ledger code, but no user-facing screen was found |

Invoice voiding and payment reversal are administrator-protected and audited.

# 20. Common User Mistakes

Common mistakes include selecting learner invoice mode when a parent aggregated invoice is needed, failing to link learners to a parent, selecting or typing the wrong grade, assigning incorrect fees, using the wrong billing period, repeatedly clicking Generate Invoice, recording a payment against the wrong learner, entering duplicate payment references, sharing passwords or OTP codes, leaving a session open on a shared computer, and running production without required environment configuration.

# 21. Recommended Daily Workflow

1. Log in securely.
2. Review the Dashboard for unusual balances or activity.
3. Confirm parent and learner records.
4. Check each learner's grade and class.
5. Confirm parent-learner links before billing.
6. Review the learner's fee profile.
7. Choose the correct invoice type: parent aggregated or individual learner.
8. Review the invoice and line items before distribution.
9. Record payments against the correct learner.
10. Open receipts or statements when needed.
11. Review reports and reconciliation exceptions.
12. Log out, especially on shared computers.

# 22. Month-End Workflow

The Month-End screen can trigger monthly invoice generation for active learners with assigned fee profiles. The screen says there is a scheduled run on the first of each month at 00:05 Africa/Windhoek. The scheduler code exists, but the current app entry point does not visibly start it, so automatic scheduling should be verified in the deployment environment before relying on it.

Recommended month-end process:

1. Check learner records and active statuses.
2. Verify grades and classes.
3. Confirm parent links.
4. Validate fee assignments in Fee Catalogue -> Learner Profiles.
5. Trigger the month-end run for the correct billing period.
6. Review run history and processing logs.
7. Check skipped learners.
8. Review invoice totals and ledger reconciliation.
9. Check unpaid balances.
10. Generate reports.
11. Back up the database.
12. Review audit logs.

The system automatically skips learners already invoiced for the selected period in the learner month-end flow. Manual review is still required for links, fees, reports, and exceptions.

# 23. Security Responsibilities of Users

Users should use strong passwords, protect authenticator codes, never share QR codes, never share reset links, log out on shared devices, verify the site address before entering credentials, report suspicious activity, avoid writing passwords in visible places, use the correct roles and permissions, and protect exported reports because they contain financial and personal information.

# 25. System Limitations and Remaining Risks

| Severity | Risk |
| --- | --- |
| Critical | Empty databases are seeded with a known demo administrator login. This must be changed before real use. |
| High | The login page displays demo credentials, which is unsuitable for production. |
| High | Data Import routes reference `models.ImportJob`, but that model was not found. Import completion and import history may fail. |
| High | SMTP and SMS settings fields are named encrypted, but the settings route stores submitted secrets directly. This should be treated as not fully protected. |
| Medium | Payments UI has an edit action, but no backend payment update endpoint was found. |
| Medium | Page routes render the HTML shell without authentication; protected data still requires API authentication. |
| Medium | Month-end scheduler code exists, but `app.main` does not visibly start it. Manual month-end is confirmed; automatic schedule needs deployment verification. |
| Medium | Learner grade filtering exists in the API, but the Learners screen does not provide a dedicated grade dropdown. |
| Medium | Parent primary relationship is modeled but not selectable in the UI. |
| Medium | Discount, waiver, credit, and adjustment workflows are not user-facing. |
| Low | Some modal wording says delete is irreversible, while backend behavior is soft void/deactivation/reversal. |
| Low | Email modal says simulated even though backend can send real SMTP when configured. |
| Low | Password policy is minimum-length only. |

Based on these risks, the system should not be described as fully production-ready without remediation and deployment verification.

# 27. Final User Checklist

Before completing a billing operation, confirm:

1. The correct parent is selected.

3. Each learner has the correct grade.
